# Use Case Description — Edit Itinerary (UC-ADM-07)

> 입력: `docs/requirements.md`, `docs/UseCaseModeling.md` §2-2 / §3 / §4
> 대상 Req: ADM-402 / NFR 실시간 동기화 / NFR 데이터 정합성
> 개정: ISO 29148:2018 검토 #1 반영 (Singular, Conforming, Unambiguous, Complete, Verifiable, Appropriate, Cancel 분할)
> 생성: 2026-04-25

---

```
Use Case Name : Edit Itinerary

Summary : 에이전시 운영자는 환자 여정 일정을 수정하여 해당 환자와 배정된 모든 실무자에게 갱신된 스케줄이 보이도록 한다.

Actor : 에이전시 운영자 (Agency Operator)

Dependency :
  - Authenticate User
  - Synchronize Realtime State
  - Send Push Notification
  - Audit Log Action

Precondition :
  1. 에이전시 운영자가 유효한 인증 세션과 Agency Admin 권한으로 식별되어 있다.
  2. 대상 환자 케이스가 ACTIVE 상태이며 영속화된 일정 항목이 1개 이상 존재한다.
  3. 대상 일정 항목이 다른 운영자에 의해 편집 락에 걸려 있지 않다.
  4. 해당 케이스의 실시간 동기화 채널이 열려 있다.
  5. 푸시 알림 게이트웨이가 애플리케이션 서비스에서 도달 가능하다.
  6. 감사 로그 저장소가 쓰기 가능 상태이다.
  7. 시스템은 정의된 재시도 정책과 변경 diff 포맷을 적재한 상태이다 (부록 §1·§2 참조).

Description :
  1. 시스템은 Authenticate User 결과를 확인한다.
  2. 에이전시 운영자는 케이스 대시보드에서 대상 일정 항목을 선택한다.
  3. 시스템은 일정 항목에 편집 락을 획득한다.
  4. 시스템은 현재 스케줄을 편집 가능한 폼과 함께 반환한다.
  5. 에이전시 운영자는 시작 시각, 종료 시각, 장소, 배정 실무자 식별자를 포함한 수정 필드를 제출한다.
  6. 시스템은 페이로드 스키마, 비즈니스 규칙, 형제 항목과의 시간대 중복을 검증한다.
  7. 시스템은 일정 저장소에 새 리비전을 기록한다.
  8. 시스템은 일정 항목의 version 필드를 1만큼 증가시킨다.
  9. 시스템은 배정 실무자 연관을 제출 값으로 갱신한다.
 10. 시스템은 운영자 식별자, 변경 전후 diff (부록 §2 포맷), ISO 8601 타임스탬프와 함께 Audit Log Action 을 include 한다.
 11. 시스템은 구독 중인 환자 및 배정 실무자 클라이언트에 갱신된 스케줄 스냅샷을 5초 이내 전송하기 위해 Synchronize Realtime State 를 include 한다.
 12. 시스템은 배정된 모든 실무자와 환자 매직 링크 엔드포인트로 변경 알림을 큐잉하기 위해 Send Push Notification 을 include 한다.
 13. 시스템은 일정 항목의 편집 락을 해제한다.
 14. 시스템은 갱신된 일정 뷰를 에이전시 운영자에게 반환한다.
 15. 시스템은 대시보드 준비 상태(부록 §3 정의)로 복귀한다.

Alternatives :
  A1. 6 단계에서 스키마 오류·과거 시각·형제 항목 중복으로 검증이 실패하면, 시스템은 필드 수준 오류 마커와 함께 제출을 거부한다. 5 단계로 복귀한다.
  A2. 7 단계에서 다른 운영자의 동시 편집으로 version 정수 비교 기반 낙관적 락 충돌이 감지되면, 시스템은 쓰기를 중단하고 최신 리비전을 다시 로드해 머지 뷰를 표시한다. 4 단계로 복귀한다.
  A3. 11 단계에서 실시간 동기화 발행 호출이 실패하면, 시스템은 부록 §1 재시도 정책에 따라 재시도한다.
       A3.1. 최종 실패 시 시스템은 지연 발송 큐에 delta 를 기록한다.
       A3.2. 시스템은 응답에 degraded_sync 플래그를 설정한다.
       A3.3. 유스케이스를 degraded_sync 플래그가 설정된 채로 종료한다.
  A4. 12 단계에서 푸시 알림 게이트웨이가 5xx 응답을 반환하면, 시스템은 부록 §1 재시도 정책에 따라 알림을 재시도 큐에 등록한다.
       A4.1. 재시도가 모두 소진되면 시스템은 실패를 알림 센터에 기록한다.
       A4.2. 시스템은 진행을 계속한다. 13 단계로 복귀한다.
  A5. 4 단계와 7 단계 사이에서 에이전시 운영자가 편집을 취소하면, 다음을 순차 수행한다.
       A5.1. 시스템은 임시 페이로드를 폐기한다.
       A5.2. 시스템은 편집 락을 해제한다.
       A5.3. 유스케이스를 종료한다.
  A6. 1 단계에서 RBAC 검사가 대상 케이스에 대한 쓰기 권한을 거부하면, 다음을 순차 수행한다.
       A6.1. 시스템은 행위를 차단한다.
       A6.2. 시스템은 운영자 식별자와 거부 사유와 함께 Audit Log Action 을 include 한다.
       A6.3. 시스템은 권한 오류 코드를 반환한다.
       A6.4. 유스케이스를 종료한다.
  A7. 3 단계에서 다른 편집자가 락을 보유 중이라 락 획득에 실패하면, 시스템은 락 보유자 식별자를 포함한 lock_held 오류를 반환한다. 유스케이스를 종료한다.

Postcondition :
  1. 일정 저장소의 대상 항목이 갱신되고 version 필드가 단조 증가한다.
  2. 배정 실무자 연관이 제출된 식별자를 반영하며 고아 행이 존재하지 않는다.
  3. 감사 로그 저장소에 운영자 식별자·변경 전후 diff·ISO 8601 타임스탬프 항목이 영속화된다.
  4. 정상 동기화 시: 구독 중인 환자 및 배정 실무자 클라이언트에 5초 이내 실시간 스냅샷이 전달된다.
  4a. 동기화 실패 시 (A3): 응답에 degraded_sync 플래그가 설정되고 지연 발송 큐에 delta 항목이 등록된다.
  5. 배정된 모든 실무자 식별자와 환자 매직 링크 엔드포인트에 대해 푸시 알림 작업이 큐잉된다.
  6. 일정 항목의 편집 락이 해제된다.
  7. 검증·락·권한 실패 종료 시 (A1, A2, A6, A7): 일정 저장소 레코드가 변경되지 않고, 본문 변경에 대한 audit diff 가 기록되지 않으며, 알림이 발송되지 않는다.
  8. 취소 종료 시 (A5): 임시 페이로드가 폐기되고 편집 락이 해제되며 일정 저장소 레코드가 변경되지 않는다.
```

## 부록

### §1. 재시도 정책 (Unambiguous / Verifiable 보강)

- 알고리즘: 지수 백오프 (exponential backoff)
- 초기 지연: 1 초
- 배수: 2
- 최대 시도 횟수: 3 회 (= 1초 → 2초 → 4초 간격)
- 종료 조건:
  - 성공 응답 수신 시 즉시 종료
  - 3회 모두 실패 시 본문에 정의된 fallback 단계 진입
- 적용 대상: A3 실시간 동기화 발행 / A4 푸시 알림 게이트웨이 호출

### §2. 변경 전후 diff 포맷 (Unambiguous 보강)

- 표준: JSON Patch (RFC 6902)
- 필드: `op`, `path`, `value` (op ∈ {replace, add, remove})
- 적용 대상: 감사 로그 저장소에 기록되는 변경 본문
- 예시:
  ```
  [
    { "op": "replace", "path": "/start_time", "value": "2026-04-26T09:00:00Z" },
    { "op": "replace", "path": "/assigned_staff/0", "value": "STAFF-1138" }
  ]
  ```

### §3. 대시보드 준비 상태 정의 (Verifiable 보강)

다음 조건을 모두 충족한 상태:
1. 대상 일정 항목의 편집 락이 해제됨
2. 갱신된 일정 데이터의 신규 fetch 가 가능함
3. 다음 운영자 입력을 받을 수 있는 입력 대기 상태

# UC-ADM-07 L5 코드 생성 프롬프트

현재 열려 있는 저장소는 대학원 AI 기반 소프트웨어 개발방법 수업의 팀 프로젝트다.

이번 작업은 L4 Object Structuring 코드에 L5 Dynamic Modeling 명세를 적용하는 재현성 검증 실험이다.

## 단일 기준 명세

`Output_L5/docs/WS3_RED-SHA_K-MedTour_DynamicModeling.md`

* UC-ADM-07 Edit Itinerary
* 시스템명: K-MedTour
* 팀명: RED-SHA

구현 대상 기준 코드는 다음 폴더다.

`Output_L3+L4`

먼저 다음 자료를 읽는다.

* Output_L1
* Output_L2

* Output_L5/docs/WS3_RED-SHA_K-MedTour_DynamicModeling.md

기존 L4 클래스, 패키지, 객체 책임과 실제 메서드 및 DTO 필드를 확인한 후 구현한다.

## 구현 원칙

1. `WS3_RED-SHA_K-MedTour_DynamicModeling.md`에 정의된 메시지 번호와 호출 순서를 따른다.

2. 주요 객체 호출 위치에 L5 메시지 번호를 Java 주석으로 기록한다.

3. 기존 패키지 흐름을 유지한다.

   `ifo → http → control → dto/entity → adapter`

4. 기존 L4 클래스와 객체 책임을 임의로 합치거나 삭제하거나 이동하지 않는다.

5. 관련 없는 클래스, 문서, 패키지를 수정하지 않는다.

6. 전체 프로젝트를 임의로 리팩터링하지 않는다.

7. 코드 포맷을 이유로 관련 없는 파일 전체를 변경하지 않는다.

8. 외부 라이브러리나 프레임워크를 추가하지 않는다.

9. Java 표준 라이브러리와 기존 프로젝트 구성만 사용한다.

10. L1, L2, L3, L4 문서는 수정하지 않는다.

11. `WS3_RED-SHA_K-MedTour_DynamicModeling.md`와 현재 프롬프트 파일은 수정하지 않는다.

12. 현재 브랜치명이나 실험 run 번호를 Java 코드, 클래스명, 주석에 넣지 않는다.

## 메시지 상호작용

1. L2의 정수 단계 번호를 유지한다.
2. 내부 객체 호출은 소수 번호로 구현한다.
3. `concurrent` 출력은 동일한 상태 전이에서 선후 의존성이 없는 출력으로 구현한다.
4. `ACK`는 명세에 실제로 정의된 경우에만 구현한다.
5. 명세에 없는 ACK 또는 비동기 처리를 임의로 추가하지 않는다.
6. 메시지 호출 경로를 임의로 단축하지 않는다.

## Aggregate DTO

1. 기존 DTO로 명세를 충족할 수 있으면 기존 DTO를 우선 사용한다.
2. 기존 DTO로 충족할 수 없는 경우에만 신규 DTO를 생성한다.
3. DTO 필드와 Java 타입은 L3 Entity 및 L5 명세와 일치시킨다.
4. DTO는 가능한 한 불변 객체로 구현한다.
5. DTO에 업무 처리 메서드를 추가하지 않는다.

## Statechart

1. 상태 종속 Control 객체에는 명시적인 상태 타입을 구현한다.
2. 상태 변경은 지정된 전이 메서드를 통해서만 수행한다.
3. 각 전이에서 현재 상태, 이벤트, 가드, 다음 상태를 검증한다.
4. 허용되지 않은 상태 전이는 거부한다.
5. Cancel, Failure 등 공통 전이는 명세된 Superstate의 의미를 반영한다.
6. 여러 메서드에 동일한 취소 및 종료 로직을 무분별하게 중복하지 않는다.

## Alternative 처리

1. L2의 모든 Alternative를 명세된 Exception, Status, ErrorCode, Warning 또는 정상 취소로 매핑한다.
2. 정상적인 업무 거절, 버전 충돌, 잠금 충돌 및 사용자 취소를 일반 RuntimeException으로 처리하지 않는다.
3. 보안 위반이나 복구할 수 없는 기술 오류만 명세에 따라 Exception으로 처리한다.
4. HTTP 상태코드는 L5 명세와 일치시킨다.
5. 실시간 동기화 또는 푸시 알림 실패가 핵심 일정 변경 성공 여부에 미치는 영향을 명세대로 구현한다.

## 동시성 및 자원 처리

1. 편집 잠금, 현재 버전 확인, 수정값 검증, Entity 변경, 버전 증가 및 저장의 원자성을 명세대로 구현한다.
2. 검증과 변경 사이에 다른 요청이 개입하지 않도록 한다.
3. 잠금은 성공, 거절, 취소 및 예외 상황에서 모두 해제한다.
4. 잠금 해제는 `finally` 또는 이에 준하는 안전한 구조에서 수행한다.
5. 다중 락이 필요하면 명세된 고정 순서로 획득한다.
6. 실시간 동기화와 푸시 알림 같은 외부 처리는 명세에 따라 핵심 임계영역과 분리한다.
7. 성공, 업무 거절 및 예외 상황에서 감사 로그 처리 여부를 명세대로 구현한다.

## 변경 범위

가능한 최소 범위만 변경한다.

신규 클래스가 필요한 경우 다음 조건을 만족해야 한다.

* 기존 클래스로 책임을 표현할 수 없는 명확한 이유가 있어야 한다.
* 기존 패키지 구조를 따라야 한다.
* 최종 결과에 신규 클래스가 필요한 이유를 설명해야 한다.

## 빌드 및 검증

코드 수정 후 다음 작업을 수행한다.

1. `Output_L3+L4/build.sh`를 사용해 컴파일한다.
2. 서버 실행까지 진행되면 정상 시작 여부를 확인하고 종료한다.
3. 컴파일 오류가 발생하면 명세나 구조를 임의로 변경하지 않고 오류를 수정한다.
4. 기존 테스트가 있으면 실행한다.
5. 기존 테스트 구조가 없으면 외부 테스트 프레임워크를 추가하지 않는다.
6. 생성되는 JAR 파일은 소스 변경으로 간주하지 않는다.
